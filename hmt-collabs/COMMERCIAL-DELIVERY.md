# Commercial-to-delivery workflow

Commercial & Presales now opens a customer-scoped register with record creation, stage management, award verification, project handovers, reporting and audit tiles. Existing commercial records are reused. RFQs use the existing `rfp` storage kind with an `[RFQ]` marker in notes to remain compatible with legacy schema and reporting; the new UI labels them RFQ.

An opportunity parents an RFP/RFQ; a quotation can reference either. Award verification includes the accepted quotation and its ancestor chain, with optional related source records from the same customer. Each additional accepted quotation receives its own award. Verification requires an accepted version, purchase evidence reference, scope, deliverables, project name, eligible independent manager/sponsor, and optional customer contract and delivery date. It records commercial events and an immutable award snapshot. Evidence references are recorded assertions for review; this application does not independently validate an external PO or electronically sign a contract.

After verification the service calls the existing Project Management creation endpoint. Project creation, its 22 controls, six suggested WBS tasks, source links, commercial handover and project/commercial audit are one atomic D1 batch. Award verification is a separate transaction: provisioning failure leaves a visible unconverted award and retry action. `(award_id, workstream)` uniqueness prevents repeated clicks or conversion retries from creating a second project. A separate named workstream deliberately creates another project. Existing accepted awards are not automatically backfilled from legacy `won` flags: the technical report lists won records lacking verified purchase evidence.

The accepted sales value remains in the commercial snapshot; project cost budget and effort start blank. The project manager confirms these through existing controls. Project delivery acceptance is an independent review by the assigned manager or sponsor, excluding the handover requester. Rejected handovers remain blocked and can be reviewed again after resolution. Acceptance/rejection writes project revision, decision notes, identities and audit records. Pending/rejected handovers generate in-app workflow alerts on creation, linkage and scheduled project scans. No external email/messages are sent.

Starting/completing tasks, resuming into delivery, or advancing gates requires all linked commercial handovers to be accepted. Database triggers also block task progression and stage advancement, including updates from other API routes. Generic handover-register editing cannot replace a commercial handover decision. Manual project creation remains available for internal/noncommercial work.

Additional awards can link to existing projects during initiation/planning using revision guards. Linking preserves the existing baseline and requires delivery acceptance for that award. After planning, use the project's existing independently approved change process; automatic post-baseline commercial amendment application is not implemented. Separate workstreams inherit the awarded scope as a starting point and must be tailored and reviewed before planning approval.

Regional Reporting contains three new reports (44 total): Financial — Awards & project conversion; Technical — Commercial delivery handovers; Audit — Commercial-to-delivery audit. Existing project financial/delivery/control/audit reports also include handover context. Accepted sales value is one row per award in the commercial report; do not sum repeated award values across workstreams, and verify whether multiple quotation versions replace rather than supplement each other. No revenue recognition, invoices, payments, FX conversion or margin calculation is inferred.

Authorization reuses internal project roles, country scope and existing report permissions. Commercial register operations require leadership access; delivery decisions additionally require assigned manager/sponsor and independent reviewer. Nonfinancial project members do not receive accepted quotation amounts in project detail snapshots. Origin checks and parameterized SQL apply to writes; limits apply to request size, source lists and report detail rows.

Migration: `migrations/commercial-delivery.sql` is additive and idempotent. Preserve the complete live multipart Worker and existing inherited bindings during deployment. Editable HTML and generated JS page exports must remain synchronized.

Validation: `node hmt-collabs/tests/commercial-delivery.test.mjs` and `node hmt-collabs/tests/project-management-extra.test.mjs`. Tests use synthetic SQLite fixtures and stub authentication, never production bypass credentials. They cover source chains, country/Origin access, snapshots, automatic creation, controls, retries, multiple workstreams, combined awards, revisions, delivery acceptance/rejection, bypass protection, notifications, source edits and all 44 report query paths. Browser QA verified award form → automatic draft → linked commercial origin with synthetic data. Live signed-in customer UAT remains pending.
